# gotcha：测试必须断言**契约**，而不是断言**现状**

## 实例（2026-09-20）

`tests/test_element_size_adjudicate.py` 里有一条真实产物用例，断言：
```python
strcount = [r for r in rows if isinstance(r['raw_site']['count'], str)]
assert strcount, '真实产物应含字符串 count'      # ✗ 把缺陷固化成期望
```
当时 `count` 确有 **2 条是 `str`**（asm 行 300295 `push ecx`、300859 `push ebx`）——那是**契约缺陷**（工具 docstring 声明 `count:int`）✓。
后来上游按评审条件把契约统一为 `count: int|None` ⇒ **这条测试反而失败** ✗（`9 passed, 1 failed`），
而它失败的原因**不是回归**，是它**断言了旧契约** ✓。

## 同类陷阱

1. **"真实产物应含 X"** 型断言：把当前（可能错的）产物形态当作规格 ✗
2. **黄金文件/快照测试**：上游修好后需要**主动**更新，否则变成"阻止修复的锁" ✗
3. **对缺陷的注释化描述**（"字符串 count 也必须原样进 raw 层"）✗ —— 注释解释的是缺陷，不是契约 ✓

## 规则

1. 断言写**契约**：`count` 必须是 `int|None` ✓（正向、可证伪 ✓），而不是"必须存在字符串 count" ✗
2. **上游契约变更时，必须主动搜索并翻转"断言旧契约"的测试** ✓
   （检索面：`isinstance(..., str)`、`== '...'`、快照文件、以及所有"应含/应为现状"型断言 ✓）
3. **契约变更的落地清单应含"翻转旧断言"这一步** ✓ —— 本次的做法：上游修好 ⇒ 重生成其产物 ⇒
   **重跑下游确定性工具** ⇒ 翻转"断言旧契约"的用例 ⇒ 一并提交 ✓
4. 反向自检：**故意破坏契约（如把返回值接进 `sys.exit`）时，测试必须失败** ✓ ——
   若仍全绿，说明该测试断言的是现状而非契约 ✗（本仓 T1 的 F3 就是靠这个方法发现三个测试**零判别力** ✓）
