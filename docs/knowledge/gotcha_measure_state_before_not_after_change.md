# gotcha：诊断"改动前后"时，**先确认你量的是哪个状态**

## 现象（本会话三次）

工具 `tools/cascade_plan.py` 的接口是"**从当前状态出发，求某个新尺寸的级联**"。

1. 落地 `UIStatic 152→248` **之后**，我又跑 `build_plan('UIStatic', 248)` 想看影响面 ⇒
   得到 **Δ 全 0** ✗（因为已经在 248 了）⇒ 我据此说"这些类的 Δ 为 0"，**是假象** ✗。
2. 为了查"某类是否按值持有 UIStatic 族成员"，我遍历成员并比对 `delta_of` ⇒
   **0 hits** ✗ —— 同一原因（Δ 全 0）⇒ 我差一步就写下"该类 0 个成员却涨了 192，模型有 bug" ✗。
3. 更早：我为了确认 `UISceneMap` 的"注解自相矛盾"，量的是**批次已平移后**的文件 ⇒
   报"成员末端 1204 > size"✗，而**原始注解自洽（末端 1012 == size）** ✓ ⇒ 结论**整个反过来** ✗。

## 规则

- **任何"前后对比"的结论，先写清楚量的对象是哪个状态** ✓（原始 HEAD？批次后？已落地？），
  并**从该状态重新取数**（`git show HEAD:<path>` ✓ 或显式构造 base ✓）。
- 工具若以"当前状态"为基准（Δ 型接口），**求"已应用过的变更"必然给 0** ✗ ⇒
  要看结构，就**换个幅度**（如 248→344 ✓）或对**原始副本**跑 ✓。
- 与 [[page:gotcha-annotation-authored-names-are-claims-not-evidence]] 并列：
  **结论错误往往不是推理错，而是"量的对象"错** ✓ —— 先问"这份数据是哪一刻的" ✓。
