# 用"成员名投票"判函数归属会被**传递访问**污染

## 现象

想自动化项目规则里的判据「函数内 `this->member` 引用的成员在目标类存在、且不在原类存在」，
很自然写成：取 decomp 里所有成员样式标识符（`m_X`/`p_m_X`），看它们属于哪个注解类，投票定归属。

**初版在 3395 个注解方法上跑出 273 个"重归属候选"** —— 几乎全是**假阳性**。

## 原因

Hex-Rays 会用成员名给局部变量命名，而函数**合法地访问别的对象的成员**：

```c
this->m_pRoleObj->m_Actor ...      // m_Actor 属于 Actor，但函数是 Role 的方法
p_m_bCreated = ...                 // 来自 PalScript *v1，而不是 this
```

⇒ **"某成员属于类 X" ≠ "函数属于类 X"**。文本级匹配会把整条 `a->b->c` 链上的名字都算进来。

## 正确口径

**只认"从 `this` 派生的证据"**：

* 局部变量表里名字形如 `m_*` / `p_m_*`（Hex-Rays 的局部名来自它被赋值的表达式，出自 `this->m_X` 才长这样）；
* 独立的 `p_m_*`（"指向成员 m_X 的指针"，通常出自 `&this->m_X`）；
* **明确排除**文本里的 `->m_X` / `.m_X` 形态。

按这个口径重跑，273 个候选 **归零** —— 也就是说：**对 `this->` 出现 0 次的函数，
这条路给不出任何证据**，必须逐个人工/IDB 级分析。

## 教训

1. **自动化一个判据时，先问"我抓的是不是它字面要求的那种访问"**。规则写的是 `this->member`，
   那就只能抓 `this->`。
2. **候选数突然很大时要先怀疑度量本身**（273 个 vs 项目历史上一批批几十条的量级不符）。
3. 收紧前**不要批量落盘**：本工具默认只报告，写入要显式 `--write-batch`，这条设计救了这一轮。
