# decision：布局是**基座**，进度必须双轴追踪

## 缘起（2026-09-22，一次被使用者纠正的度量近视）

修好 5 个类的布局（`UIListBox` 尺寸 +12 及其 26 个按值内嵌者的传播）后，`L1` 仍 36、总错误仍 2150 ⇒
我据此答"收益 ≈ 0" ✗ —— **这是用滞后指标否定基础性工作**，正是本会话复盘批评过的毛病（反向再犯）✗
使用者指出："**内存布局的正确很关键**" ✓

## 量化（先行指标）

| 量 | 数值 |
|---|---|
| 91 个布局冲突类覆盖的函数 | **1501 / 3598 = 42%** ⇒ 这些函数**结构上不可能字节一致** ✗ |
| 一次修复（5 类）解锁 | **140 个函数** ✓ |
| 其中单元已绿、可立即比对 | 2 个（`UIRoleSelect`，也是本轮唯一字节变化所在 ✓ 完全对应）|
| 全语料"类布局一致"的函数覆盖 | **2097 / 3598 = 58%** |

## 为什么布局是**硬上限**

1. 偏移错 ⇒ 编译出的 `[reg+disp]` 与二进制不同 ⇒ **任何函数级修补都无法匹配** ✗（不是效率问题，是可能性问题）
2. **上游性**：类型/函数/codegen 的结论都建立在偏移之上 ✓
3. **传播性**：按值内嵌会把错误沿 DAG 放大（`UIListBox` +12 ⇒ 26 个内嵌者全部后移 ✗）
4. **廉价可验证**（编译器裁判 `offsetof` ✓）且**一次修好永不返工** ✓
5. 与仓规一致：*"在 Phase 1 做所有能做的标注，即使某些信息在 Phase 1 不会立即产生收益"* ✓

## 双轴进度模型（照此追踪）

| 轴 | 指标 | 命令/来源 |
|---|---|---|
| **先行（结构）** | 布局一致类数 · **被阻塞函数数** | `tools/audit_type_layout.py`（`--json` 汇总）|
| **滞后（字节）** | `L1` · `partial` | `pipeline/cli.py match` / `s4_baseline.json` |
| **转化率** | **P(该单元 S2 绿)** —— 绿则立即兑现，否则**冻结积压** | `probe_census.json` 的单元状态 |

**实测标定**：一次 5 类修复 → 140 函数解锁，但仅 2 个单元绿 ⇒ 转化率 ≈ **1.4%** ✗ ⇒ **冻结积压**是主要形态 ✓

## 因此的作业规则

1. **不要停修布局**（它是基座 ✓）；但**要与"把已修好的单元弄绿"交替** ✓
2. **优先选修绿单元里的类**（每次修复立刻可测量 ✓）
3. 报进度时**两个轴都报**：只报 L1 会低估结构工作 ✗；只报"冲突类数"会高估字节收益 ✗

## **何时使用**
* 评估"某轮修复有没有收益"时：先问**它动的是先行轴还是滞后轴** ✓
* 看到"修了很多但 L1 不动"：查**转化率**（单元是否绿）⇒ 若低，下一步是**弄绿单元**，不是怀疑修复 ✗
* 规划工作顺序时：先用**被阻塞函数数**排序（先行），再用**单元绿否**筛（可否兑现）✓
