**现象**：为验证 VC6 mangler 的修复，写了离线测量台 `tools/mangler_bench.py`（复用 `/tmp/ua/*.obj` 的 56 个编译产物，避免每次占用 IDB 窗口重编）。测量台**自己复刻了一份 `compare_pal3.build_mangled_map`** 的逻辑。结果是：

- 在真实现里加了一处修复（从"name 本身已是 mangled 名"的 decomp 条目里解析类/方法名）后，
  **单测命中**（`mangle(...)` 产出与真实符号逐字符相同），
- 但**测量台显示 +0**，
- ⇒ captain 一度判定「该分支没用」，差点回滚一个**正确且有 +4 命中收益**的修复。

真因：测量台复刻的那份逻辑**没有同步这处修复**（它真的、独立地、复制了一份不含修复的代码）。

**为什么**：
离线测量台的价值来自"不占用稀缺资源（IDB 单写者窗口）就能高频复测"，代价是它必须**独立于管线**运行。
一旦它**复制**（而非**复用**）被测逻辑，两边就会漂移：管线改了、测量台没改，
测量台就变成"测量另一个程序"——**它测的不是你改的东西**。
这类假象特别危险，因为它**看起来是可信的负结果**（"我加了修复但指标没动"），
比崩溃更难发现，且会诱导人**回滚正确的修改**。

**何时使用 / 操作规程**：
- 写任何离线测量台/对比脚本时，**优先 `import` 复用被测的真实函数**（本例：
  `sys.path.insert` 后 `import compare_pal3 as cp; cp.build_mangled_map(idx)`），
  **不要复制**其逻辑。
- 若因依赖太重无法 import，则必须在测量台里显式标注"本文件复刻了 X 的逻辑，
  X 变更时**必须同步**"，并在每次改 X 后**用一个已知的正例校准测量台**
  （本例的正例是 `?PushOpen@AStarPathFinder@@QAEHPAUNODE@1@@Z`，单测必须 MATCH）。
- 判据顺序：**先单测（正例 MATCH）→ 再看测量台数字**。若单测 MATCH 而测量台不动，
  **先怀疑测量台**，不要怀疑修复。

## 附：同类陷阱——"比例/规模"必须先逐样本核验（2026-09-15 追加）

**现象**：我曾报告"抽样 60 个函数，**30%** 的 IDA 函数边界错位（结束地址处不是 `ret`）"，
并以此作为"需要函数范围标注机制"的主要依据。**该数字是假的**：
用稳健判据复测 ⇒ **60/60 = 100% 正常，可疑 0 个**。

**为什么**（两次测量各自的方法缺陷）：
1. **分类口径错**：把 `jmp` 结尾的 **thunk / `noreturn`** 误判为错位；正则里的 `(bad)`
   把任何反汇编错位都算进去；未排除 padding。
2. **抽样方法错（更致命）**：取 `objdump` 输出的**最后一行**判断结束指令——
   而 **`objdump -d` 从任意起始地址反汇编会产生"错位假指令"**
   （实测得到 `roll $0x89,(%eax)`、`lcall *-0x3d(%esi)`），
   **真正的 `ret` 就在它前一行**，被丢掉了。
   逐个核验那 5 个"疑错位"后 ≥3/5 其实是 `ret`：
   `ui_col_init_40FE90` → `0x40FEC8: c3 ret`；`accessor_0041D8E0` → `0x41D8EA: c3 ret`；
   `?GetRenderFlag@CCBSystem@@QAEHXZ` → `0x51337C: c2 04 00 ret $0x4`。

**⇒ 规程（必须遵守）**：
- **报任何"比例/规模"前，逐个核验 ≥3 个样本的真实性**，不能只看聚合数字；
- **不要取单一"末行"**——用**稳健判据**（多看几行、交叉验证多种信号）；
- **区分"异常读数"与"真异常"**：异常常来自**我自己的工具/口径**（见本文件主条），
  不是数据。**本会话同一类错误犯了 3 次**（30% → 8% → 0%）。

## 附二："改后读数"必须核验其文件 mtime（2026-09-15 追加）

**现象**：为测一处注解改动的效果，我读了 `data/status/baselines/latest.json` 当"改后"值，
得到 `ok=56 / err=3703`，并据此写了"Δ 全为 0"的结论表。**该表无效**——
因为 `probe` **检测到退化后拒绝刷新基线**，`latest.json` 的 mtime 仍是**改动之前**
⇒ 我读的是**改前值**。

**为什么特别危险**：它让"改动无效"这个**错误结论**看起来有数据支撑
（"我加了注解，指标一动没动 ⇒ 注解无用"），从而**误导人放弃正确的改动**。
与本文件主条（复刻被测逻辑）**同族**：都是"测量的东西不是你以为的东西"。

**⇒ 规程**：
- 读任何"改后"产物前，**先 `stat` 它的 mtime，确认在改动之后**；
- 优先读**由本次运行直接写出**的产物（例：`probe_census.json` 由 `probe` 当次写出），
  而不是"可能被拒绝刷新"的汇总文件；
- 若某门禁会**拒绝刷新**产物（如 `probe` 遇退化时不刷新基线），
  **必须显式标注**"该文件未反映本次改动"，不能当作本次读数。

## 附三："基线不可复现"时必须先重建可比口径（2026-09-15 追加）

**现象**：本会话后半段出现 `ok 56 → 51`、`L1 14 → 6` 的大幅回退，
而我连续两轮把原因归错（先归"F2 注解"、再归"`mangled_map` 键冲突"），**两次都被实测推翻**。
最终用 **`cli.py init --force`（从 `PAL3.exe.raw.i64` 干净重建）** 验证：**回退依然存在**
⇒ 排除"注解"与"`apply` 累积污染"；随后又逐一排除"我的 `emit_headers` 改动"（回退后错误数不变）
与"键冲突"（离线 diff 键集合完全相同）。

**为什么重要**：**基线本身在动时，任何改动的效果都无法测量**。
本会话因此**浪费两整轮**（先"建基线"、后"查回退"），而 F2 的效果**至今未测**。

**⇒ 规程**：
- 动手改任何东西前，**先确认当前基线能在同一口径下复现**（重跑一次完整管线取数）；
- 出现无法解释的回退时，**优先 `init --force` 干净重建**，以区分"环境/累积污染"与"真实改动造成"；
- **`probe_census.json` 不被 git 跟踪 ⇒ 没有历史可比**。
  若要追溯"某文件何时从 passing 变失败"，**必须自己在每次 probe 后归档 census**
  （落到 `data/status/` 带时间戳的副本并纳入版本控制）。

  · 附四：**回归门按 `(code,line)` 比较 + 只比计数 ⇒ 两类假回归**（2026-09-18 一次落地同时撞上两条）
    - **行号漂移**：生成文件增删一行，同一条错误 668→667 被判成"新增+已消失"。实证：`RoleAtt.cpp` 的
      `C2664 'Init'`（忽略行号的 `(code,msg)` 比对显示它基线就在）。
    - **跨文件搬移**：方法体在文件间迁移时，`A.cpp` −20 / `B.cpp` +20 被报成"B 新失败"。
      实证：`UIProgressBar.cpp` 20 errors→ok、`UI3DCtrl.cpp` 0→21，`(code,msg)` 多重集**完全相同 20 条**。
    - **正确判法**：先按 `(code,msg)` 多重集（**忽略行号**）比较，再对"搬移"做**跨文件多重集抵消**，
      剩下的才是真回归。本次真增量只有 2 条（`C2059` 单段限定名调用点 + `C2660 QueryState`）。
