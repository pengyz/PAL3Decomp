# gotcha：全局对象成员访问 = 绝对地址；且 IDA 用**符号名**渲染它

## 现象（2026-09-22，被编译器当场抓住）

对 `SceneMgr` 的 6 个成员做"无访问证据 ⇒ 撤类型"的**等值**改动后，编译错误 **+1**：
`PAL3.cpp(2725) C2440 '=' : cannot convert from 'int' to 'char [4]'`，对应生成源码：

```c
g_SceneMgr.m_nTodo_1428 = ((PAL_GDB *)&g_pGDB)->PAL_GDB::GDB_GetSkillNum(82301);
```

⇒ 该成员**确实被写入** ⇒ 我的"无证据"是**假阴性** ✗

## 两种编码形态（第一种被覆盖，第二种被漏掉）

| 形态 | 编译后 | 偏移是否作为独立 disp32 出现 |
|---|---|---|
| 经 `this`/指针 | `[reg+off]` | **是** ✓ ⇒ 偏移模式扫描可见 |
| **经全局对象** `g_X.member` | `[g_X_addr + off]`（**绝对地址**）| **否** ✗ ⇒ 偏移扫描**必然看不见** |
| 批量拷贝/序列化 | `memcpy/memset` 覆盖区间 | 否 ✗（仍是盲区，须披露）|

**实测**（MCP `find_bytes`）：
* `g_SceneMgr` = **0x00C04390**；`+0x1420` → `0xC057B0` **命中 1**；`+0x1428` → `0xC057B8` **命中 4** ✓
* 而单独搜偏移 `28 14 00 00`（disp32=0x1428）**0 命中** ✗

## ⚠️ 第二个坑：IDA 渲染绝对地址用**符号名**

承载指令的反汇编文本是 `mov dword_C057B4, 1` ⇒ **根本没有 `0xC057B4` 字样** ✗
⇒ 只匹配 `0x...` 的确认逻辑**必然失配**（这正是工具一开始仍报"无证据"的原因 ✓）
⇒ 修法：确认时**同时接受"内嵌该地址十六进制数字的符号名"**（要求 ≥6 位十六进制，避免短数字误配）✓

## 正确方法（工具已实现）
1. **枚举该类型的全局对象**（`data/annotations/globals.json` 里 `type == Cls` 的**对象**，非指针）✓
2. 对每个全局 `G` 与成员偏移 `off`：搜 **`G+off`** 的 disp32 ✓（模式含**完整 32 位地址** ⇒ 判别力极高、几乎无假阳性 ✓）
3. 确认承载指令时接受 `0x...` 或**符号名内嵌地址**两种形态 ✓
4. **批量"撤类型/降级 padding"必须以编译错误为门**（`loop` 断言 errors 不增）✓ —— 本次正是这条门抓住了假阴性 ✓

## **何时使用**
* 任何"某成员没有访问证据"的结论：**必须先跑形态②**（否则会把经全局对象的访问误判为不存在 ✗）
* 任何基于反汇编文本匹配地址的检查器：**必须处理符号名渲染** ✓
* 想撤回类型/降级为 padding 时：**编译错误门 + 三形态证据**齐备才动 ✓
