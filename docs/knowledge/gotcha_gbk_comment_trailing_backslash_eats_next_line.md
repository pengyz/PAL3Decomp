# gotcha: 中文注释行末字符的 GBK 次字节为 0x5C 时，MSVC 6 会吞掉下一行

- **类型**：gotcha（平台/工具链坑）
- **首次确认**：2026-09-19（第 63 轮），修复后状态 S2 73/201 · new_failures 0 · L1 32
- **影响面**：任何被 MSVC 6 编译、且含中文注释的 `.h`/`.cpp`。本项目源码大量中文注释 ⇒ **高危**。

## 症状

编译报**与头文件内容完全对不上**的错误，例如：

```
pal3/src/Misc/UI3DCtrl.cpp(384) : error C2065: '_pal3_coerce_f32' : undeclared identifier
```

而该标识符**确实定义在** `include/pal3/ida_defs.h:104`（无条件定义、文件字节正常、无块注释、
无孤立 CR、无行尾反斜杠、`/E` 预处理输出里也确实出现了它）。
排查会一路走进死胡同：读文件、看 `#line`、量 `sizeof`、查 ODR —— **全都看不出问题**。

## 根因

MSVC 6 按**系统 ANSI 代码页（简中 = GBK）**读取源文件，而文件本身是 **UTF-8**。
GBK 是双字节编码：某些汉字/全角标点的**第二个字节正好是 `0x5C`（反斜杠 `\`）**。

C/C++ 的**行拼接（line splicing）**规则：行末的反斜杠会把**下一行**接到本行。
⇒ 如果一行 `//` 注释的**最后那个字符**在 GBK 下以 `0x5C` 结尾，**下一行就被并进这条注释**，
于是那一行（可能正是一个函数/宏定义）**整行消失**。

本次实例：`ida_defs.h` 第 98–103 行是 2026-09-15 加的中文注释块，
其中某行的末字符触发了续行，**吞掉了第 104 行的 `__forceinline float _pal3_coerce_f32(...)` 定义**；
而第 105 行的 `_f64` 无恙 —— 与"只缺 `_f32`、只报一处 C2065"完全吻合。
`pipeline/gen/ast_transform.py:930` 会把 `COERCE_FLOAT` 改写成 `_pal3_coerce_f32(...)`，
于是所有走该形态的 TU 全部编不过。

## 关键辨别手法（避免误判为"文件被改坏"）

1. **数调用点 vs 数定义点**：`grep -c _pal3_coerce_f32 <受影响.cpp>` = 2（都是使用点）、
   而预处理输出里也是 2 ⇒ **说明"定义没被发射"**（我一度以为"2 = 定义+使用"而误撤回结论，浪费两轮）。
2. **不要用 `Get-Content` 判断行尾**：PowerShell 的 `Get-Content` 按 `\r\n` 切分、`Select-String` 按 `\n` 切分，
   对**混排行尾**的文件会给出**不同行号**，还会把多行显示成一行（本坑排查中反复误导）。
   ⇒ **一律用 python**（`open(...,encoding='utf-8')` 会把 CR/CRLF 归一成 `\n`）。
3. **不要靠 `#line` 推断"整段被跳过"**：MSVC 只在需要重同步时才发 `#line`，不是每行都发。
4. **决定性验证**：把 `cl /E` 的输出**落盘成 `.i` 文件**，在里面搜定义的**函数体**（如 `return *(float *)&v;`）与标识符名，
   并打印命中处上下文 —— 一眼看出定义是否真的没进输出。

## 规避/修复

- **修复**：给可疑的中文注释行**末尾补一个 ASCII 空格**（末字节变成 `0x20`，续行不再触发）。
  纯机械、不改语义、不改中文内容。本次修 6 行即恢复。
- **预防**：中文注释行末尾**统一补一个 ASCII 空格**，或用 ASCII 标点收尾（`.`/`;`）；
  更高压的做法是让生成/编辑脚本在写回时做一次"行尾非 ASCII ⇒ 补空格"的规范化。
- **观测**：本坑很可能被"重写文件时改变行尾（CRLF→LF）"**激活**（行末字节序列变了）。
  ⇒ 用脚本重写含中文注释的仓库文件时，**务必保持原有行尾**并复核末字符。
