# pattern：字段"类型与名字"的证据分级 —— disp32 全二进制扫描

## 为什么需要（2026-09-21 使用者指令 + 实测）

使用者指出：`m_nTodo_C660` 这类名字"需要更明确的语义命名，类型也需要确认和修正"。
**实测反转了问题的定性**：`m_nTodo_C660` 的偏移 +0xC660 在整个二进制里
**disp32 模式 `60 C6 00 00` 命中 0 次** ⇒ **没有任何指令直接访问它** ⇒
它**很可能根本不是字段**（死空间/填充）⇒ 给它 `int` 类型 + `m_nTodo_` 名字**本身就是编造** ✗

（阳性对照 `m_nRoleCount` +0xE0E0 = `E0 E0 00 00` ⇒ **8 处命中** ✓ 方法有效）

## 方法（机械、可否证、证据分级）

对每个成员偏移 `off`：

1. **disp32 扫描**：把 `off` 写成小端 4 字节，用 MCP `find_bytes {patterns:[...]}` **全二进制**搜
   * **0 命中** ⇒ **无直接 disp32 访问** ⇒ `NO-EVIDENCE` ⇒
     **不得**给出类型、**不得**给出语义名 ⇒ 应作 **padding/未知空间**（或保留 `_todo_` 并标注"无访问证据"）✗
   * **有命中** ⇒ 进入第 2 步（命中含假阳性，必须确认）
2. **确认承载指令**：`disasm` 命中点附近的指令，找出**真正**包含该 disp32 的指令，并确认基址寄存器是
   `this` 派生（`__thiscall` 的 ECX，或 `mov esi,ecx` 这类缓存寄存器 ✓）
   ⚠️ **实测假阳性来源**：栈偏移（`[esp+116Ch+var_100C]`）与立即数 ⇒ 不确认就会误判 ✓
3. **定类型（可证）**：宽度（BYTE/WORD/DWORD/QWORD · `fld dword/qword` · XMM）+ 运算
   （`fdiv`⇒float · `imul`⇒整型数组 · `cmp`+`jl`/`jb`⇒有/无符号）⇒ 可证 **宽度 + int/float/指针 + 有/无符号** ✓
   **不可证**：精确源码类型（`int` vs `long` vs enum）、struct vs class ✗
4. **定名字（仅在存在"语义把手"时可证）**：字符串/诊断信息 · RTTI `??_R*` · 传给已知 API 的实参 ·
   mangled 符号 · PDB（**PAL3A≠PAL3，仅参考**）⇒ 有把手 ⇒ 名字可给（记证据指针）；
   **无把手 ⇒ NO-EVIDENCE ⇒ 保留 `_todo_`**（仓规：不确定含义时保留 `_todo_`；禁止伪语义命名）✓

  地址后缀伪名 **701** · `m_nField_*` **90** · `Unk` 14 · `_todo_` 3
* 重灾区（数据/状态容器类）：`ScriptSystemData` 118 · `tagPAL3GameState` 93 · `PalScriptMgr` 75 ·
  `tagEffMgrData` 73 · `CCBRoleState` 55 · `UIScenePanel` 45 · `SceneMgr` 32
* 类型泛化：`int` **2896（29.3%）** · `BYTE/char` 365 · `char[]` 341 · `void *` 168
  ⇒ 其中相当一部分可能属"无访问证据"，应由本流程**重新分类**（而非改个名字了事）

## **何时使用**

* 想给某个成员"改个更好的名字"之前：**先跑 disp32 扫描** —— 0 命中就不该有名字和类型 ✗
* 想修某个成员的类型时：用宽度/运算证据（步骤3），**别用反编译文本猜**（仓规：禁止仅凭 Hex-Rays 文本推断）
* 想做"批量改名"时：**不做**。名字要么有把手（可证），要么保留 `_todo_` ✓
