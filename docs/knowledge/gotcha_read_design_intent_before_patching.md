## 教训

**动手改任何代码前，必须先读该处的注释/文档/设计意图**。

代码里的注释往往写明：
- 为什么这样设计（历史背景）
- 试过什么方案（F59/F62/F63 演化链）
- 已知边界/限制（sizeof=824 是 F63 待修）

**不读注释就定性 ⇒ 重复前人已试过的错误路径**。

## 实证：emit_headers.py L3085-3120

```python
# F59（第 108 轮）：同型错位的**另一半**——注解在 +0 标的是一个"真实成员"（不是占位符）。
# 有虚函数 + 注解带 vtable ⇒ 二进制里 +0 就是编译器隐式 vfptr；
# 若头里再声明一个 +0 数据成员，它会被挤到 +4，**其后每个成员整体偏 4**。
# ...改为把它声明成 **static 成员**：静态成员**不占对象字节**
# ⇒ 编译器隐式 vfptr 独占 +0，其后成员偏移全部归位
#
# F62（第 110 轮）：尝试把门放宽到"类声明了 virtual"
# **但实测该放宽会让成员偏移更差**（SceneMgr m_nRoleCount −4→−24）
# ⇒ 说明 static 别名会打乱生成器的 _gap_ 记账，必须先修 gap 记账才能真正放宽。
# 故本轮回退到 F59 的窄门，**F63 待做**。
```

**注释已写明**：F59 设计意图 · F62 试过并回退 · F63 待做
⇒ lead 未读就定性「static 缺陷」= **重复 F62 已试过的错误路径**
