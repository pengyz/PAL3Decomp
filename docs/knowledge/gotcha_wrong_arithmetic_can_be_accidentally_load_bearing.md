**场景**：`pipeline/gen/stages/stage3_cleanup.py:501` 用
`slots.get(d['offset'] // 4)` 把 Hex-Rays 的 `obj->__vftable + N` 映射到注释里的槽位名。
而 `store.struct_vtables` 的键是**槽位下标**（`data.py:44` 注释即写明 `slot_index`）。

**我先证明了 `//4` 是错的（A 级，两条独立证据）**：

| 证据 | 内容 |
|---|---|
| 二进制对照 | `sub_4C52C0`：Hex-Rays `__vftable + 2` ⇔ asm `call dword ptr [edx+8]` ⇒ **8/4 = 2**，N 就是槽位下标 |
| 多样本 | 脚本化配对 6/9 例一致（`sub_5371B0 N=15 ↔ 60h`、`sub_536FD0 N=7 ↔ 1Ch` …） |
| 反面排除 | 855 处 `__vftable + N` 里 **639 处（75%）的 N 不是 4 的倍数**（`+3` 243 次…）；字节偏移必然 4 的倍数 ⇒ N 不可能是字节偏移 |

**然后我改了它 —— 净退化**：`probe all` + `compile_regression` 报 **2 个 ok→fail**
（`UI3DCtrl.cpp`、`UIStatic.cpp`）、1 个 fail→ok、**S2 净 −1**。已回退。

**根因不在那行算术里，而在注解不完整**：

| 类 | 注解覆盖下标 | Hex-Rays 实际引用的 N |
|---|---|---|
| `gbTexture` | **0–3** | {2, **4, 5**} |
| `gbGfxManager` | **0–6** | {2, **12,13,15,21,22,23,25,26,28**} |

- **旧 `N // 4`**：`gbGfxManager` 的 12→3、21→5、22→5、28→7 —— 把**未标注的高槽折叠进已标注的低区间**，
  于是"命中"并给出一个**名字**。这些名字多数能通过类型检查 ⇒ 文件保持 ok。**是巧合在顶住，不是正确。**
- **新 `N`**：槽 5/12/28 没标注 → 返回 None → 走 **stub 回退**，而 stub 的签名由 Hex-Rays 的 cast 合成
  （如 `int (__thiscall)(gbGfxManager *, char *)`），**与调用点实参类型不一定相符** ⇒ C2664/C2440。

⇒ 真正要修的是 **(1) DLL 类 vtable 注解缺槽位** 与 **(2) stub 回退的合成签名不是类型安全的**
（"没有注解"反而比"错的注解"更糟）。`//4` 不是任何东西的根因，它只是把 (1) 掩盖住了。

**可复用的教训（这条比 bug 本身值钱）**：

1. **在能解释"错的东西为什么产出正确结果"之前，不要改它。**
   我证明了 `//4` *错*，却没证明"它为什么让 2 个文件保持 ok" —— 于是改它必然变成试错。
   **"证明了它是错的"≠"证明了改成对的是安全的"。**
2. **"错的算术 + 侥幸命中"是一种隐性依赖**：它把缺失的数据（未标注的槽位）折叠进已有数据里，
   产生看似合理的输出。这类依赖没有任何显式记录，只有**解释清楚机制**才能发现。
3. **拿掉掩盖物之前先补洞**：正确顺序是补注解 → 让回退路径类型安全 → **再**改算术。
   我把顺序做反了，还写了个"命中就用 N、否则回退 //4"的兼容补丁 —— **那正是项目明令禁止的
   试错式修改**（改一版看指标骂不骂），已一并撤销。
4. **把发现固化成 skip 的守卫**：`tests/test_vtbl_slot_index.py` 把 3 项标为 SKIP 并写明前置条件，
   另 2 项断言**证据本身**（N = 位移/4 的实例表）。这样未来的修复者有现成护栏，
   而不是靠"记得这件事"。
