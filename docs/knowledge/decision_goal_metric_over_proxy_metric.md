# decision：用**目标指标**规划，不用**代理指标**

## 事实（2026-09-21 会话复盘，13 次提交）

| | 会话初 | 会话末 |
|---|---|---|
| S2 | 75/205 | 75/205 |
| 总错误 | 2150 | 2150 |
| matched / L1 / partial | 265/319 · 35 · 198 | 265/319 · **35** · 198 |

* 13 次提交中**只有 2 次改变了生成行为**（`::ShowWindow` 补限定 · 自由函数 `this`→`_this`），
  而**两次都落在 C1003 截断单元**（`CCBUI.cpp`/`CCBStage.cpp` · `free_functions.cpp`）⇒ **聚合指标看不见** ✗
* 另有 1 次只加注释、1 次"实现了但故意不接线"、其余为分析/校验/工具/知识/门禁。
* **而"只差 1 个字节"的 3 个函数（`FindInOpen`/`FindInClosed`/`GetEntryPtr`）在整个会话里一次都没被碰过** ✗
  ——它们是**唯一能直接变成 L1 的地方**（10 条 ≥80%，3 条 n_diff=1）。

## 因果（不是运气问题，是规划问题）

1. **规划输入用错了指标**：从"错误码家族有多大"（C2660/C2039/寄存器宏/this…）选目标，
   而错误数**既不等于字节**、又在**截断单元里失明**（3 个单元 306 条是下界）。
2. **发现失明后没有换目标选择**：会话中段已识别 C1003 盲区并做了仪表（`status` 截断表），
   但之后仍继续在**截断单元**里做族级修复（F3a、`this` 改名）⇒ 收益结构性不可见 ✗。
3. **按"家族大小"排序，而不是按"离完成多远"排序**：167（寄存器宏）/92（string 内部）/86（__vftable）…
   全都在**匹配度 <50% 或不可编译**的函数里 ⇒ 修了也不产生 L1 ✗。
4. **规划顺序是"机制优先、可判定性最后"**：F1 / F3b / F5 的**可测量前提**都是事后才发现的
   （F5 需函数可编译、F1 需成员存在、F3b 需注解元数）⇒ 每个周期都先花了预算才撞墙。
5. **仪表工作替代了目标工作**：`status`/`loop`/棘轮修复/MCP/盲区仪表都真实有用，
   但**不是朝目标推进**；本会话完成度高的是仪表，目标是 0。

## 规则（后续会话必须遵守）

1. **唯一进度指标 = `match_L1`**（字节全同函数数）。`总错误` 只作诊断，且必须注明"含 3 个截断单元的下界"。
2. **候选来源 = 近失清单**：`pct≥80%` **且** `编译长度/原始长度 ≥0.95` **且** 在 **S2 绿单元**。
   当前 10 条（3 条 n_diff=1）—— 这就是"唯一能拿到 L1 的地方"。
3. **每条的标准流程**：`s4_diff_detail.json` 的 `diffs` 偏移 →（MCP `disasm`）原指令 →
   分类（偏移错 / 寄存器选择 / 结构归属）→ 改 → `loop --stages codegen,probe,match` → **读 `match_L1`**。
   **只有第 6 步数字变了才算进度**；错误数变化不算。
4. **禁止**：在非绿单元、或 `ratio<0.95` 的函数上做族级修复（拿不到字节读数 ⇒ 收益不可证）。
5. **预算规则**：任何仪表/基础设施工作**必须先绑定一个具体测量目标**，且**完成后立刻用它推进目标一次**。
6. **否决要发生在动手之前**：用"① 能否拿到字节读数？② 该函数重建是否已接近完整？"两道前置检查，
   过不了就不做（本会话 6 次否决里 4 次是在动手之后 ✗）。

## **为什么**（反例，已实测）

* F5 寄存器族：167 条错误，但修 `_ESI` 会**揭开**被遮蔽的 `C2094`，函数不可编译 ⇒ **无字节判定**；
* 27 条"显式 this 重复发射"：改写调用形式后 `SceneProp::CalculateWorldPos` **5.5% → 5.2%**（略降），
  因为该函数**编译长度 160 / 原始 343** ⇒ 重建只有一半 ⇒ 小修无意义 ✗。

## **何时使用**

* 每次规划"下一步做什么"之前：先问"**这个改动会让 `match_L1` 动吗？动多少？**"；
* 想按错误码家族排优先级时：先跑近失清单，只有落在清单里的家族才值得做 ✓。
