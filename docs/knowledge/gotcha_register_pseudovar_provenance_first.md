# gotcha：寄存器伪变量——先查来源，再谈修法；且"修一族 ≠ 有收益"

## 现象与第一性结论（2026-09-21，全部经 IDA Pro MCP 二进制校验）

`include/pal3/ida_defs.h` 把 `_EAX/_ESI/_ET1…` `#define` 成字面量 `0`，
于是生成代码里 `_ESI = &x;` / `_ESI[1].m_teamSlotsB…` 全部报错（实测该族 **167 条**）。

**第一步必须是查来源指令**（MCP `disasm` 函数序言）：

```
0x00411E00  RoleSystem::ApplyMoveStep:
  411e07  push esi              ; 保存 callee-saved ESI
  411e08  mov esi, ecx          ; ★ ESI = this（ECX = this）
  ...
  411ef5  pop esi               ; 出口恢复
  411f4f  pop esi               ; 另一出口
```

⇒ **全程对 ESI 只有这一次写入（外加出口恢复）** ⇒ **`_ESI` ≡ `this`** ✓
⇒ 因此**正确的修法是把它替换成 `this`**（等价变换，且正是源码原貌）；
  **"声明一个局部 `RoleSystem *_ESI;`" 是伪造** ✗ —— 源码里没有这个变量，
  会让编译器产生额外的存/取 ⇒ **字节不可能一致**。

逐函数取证（11 个含伪寄存器的函数）：`ESI=this` 8 个 · `EDI=this` 1 个 · 其它（`PAL3::Update` 的 ESI/EBX 非 this）2 个
⇒ **必须逐函数**判定，不能全局假设。

## **为什么**这不是签名问题（层判定）

`export_funcs prototypes` 显示这些函数在 IDB 里**本来就是**
`void __thiscall(RoleSystem *this, double, int, float, char)` ✓ 完全正确。
⇒ 结论：**Hex-Rays 的变量分析局限** —— 它未能把"被缓存进 callee-saved 寄存器的 `this`"折回 `this`
（函数内有 6 个 call ⇒ 该寄存器跨调用存活）。**不是签名错、不是 IDB 错。**

## ⚠️⚠️ 关键：修一族会**揭开**另一族（"不报错"不是收益）

做了一次**字节判定实验**（把该函数单独放进 scratch TU、`_ESI`→`this`、临时量声明为局部、
用管线的 `/O2 /Ob2 /Oi /Ot /Oy /GF /Gy /GX /GR /MD /Gd` 编译）：

* 寄存器族修好后，**立刻新增** `C2094 label 'var_C' was undefined`（内联 `__asm` 里的栈帧名）✗
* 而**真实文件**编译时 `C2094` **0 条** —— 原因是 MSVC 在已有 102 条错误时**错误恢复跳过了 asm 检查**
  ⇒ 该族一直**潜伏**，被寄存器错误**遮蔽** ✓

⇒ **"−150 条可见错误"是幻觉**：它是"修 A 族 → 揭开 B 族"的**假位移**，
而**字节判定拿不到**（函数仍不可编译 ⇒ 无法 `match`）✗。

## 规则（本项目的第一性判据）

1. **收益的单位是"字节一致"，不是"错误数"**：`不报错 ≠ 收益`。
2. 想验证某个改写是否忠实：**必须在"可编译单元"上做字节判定**（`match`）；
   若某函数所在单元不绿，则**先把它修到能编译**（连同所有潜伏族），再看字节。
   **做不到字节判定就不要做。**
3. 判"能否还原"的正确问题不是"能不能编译"，而是"**原源码在这里写的是什么**"——
   用来源指令回答（`mov esi,ecx` ⇒ 源码写的是 `this`）。
4. 逐函数、逐寄存器取证；不要用全局类型/全局宏去"盖住"。

## **何时使用**

* 看到 `_EAX/_ESI/_EDI/_ET1` 的编译错误时：**先 disasm 看来源**，再决定"替换为 this / 替换为局部 / 不管"；
* 任何"把这些错误修掉就能拿到 N 条收益"的估算：**先检查是否被遮蔽的族**（本仓已有 C1003 截断遮蔽、
  以及本条的单文件内遮蔽）——`C2094` 的 0 条就是证据。
* 想动 F5（寄存器宏族）：**不要**以"减少错误数"为理由做；只有在"能拿到字节判定"时才做。
