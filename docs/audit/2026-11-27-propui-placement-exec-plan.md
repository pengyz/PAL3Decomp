## §0 怎么用这张清单

1. **一行 = 一个落位单元**：对象段、对齐间隙、整块建模区、尾标量各自一行；合计 48 行。
2. **「拟用名」是候选**：来自 #37 §5 的候选 A（形态直译）；无用途证据的段一律写「（待证后命名）」，不许照抄注解里的旧名。
3. **证据等级 < B 的行**：
   - 表内标「B-」或「C」，并在 §3 有补证入口；
   - **实施时不得直接给类型**（例如 84B 控件不要写成 `UIFlexBar`、344B 不要写成 `UIButton`/`NameSys`），只能先用「N 字节控件 + 校验点」占位，补证后再补类型。
4. **对齐间隙不落成员**：13 段间隙 + 尾部对齐共 252B，占真实对象的一部分但不是字段；若实现把它们并进相邻成员（例如把 16B 并进容器 buffer），必须在实施说明里写理由，验收会按 `sizeof` 重算。
5. **尺寸闭合**：48 行长度求和 = **28,892 = 0x70DC**，见 §5。

## §5 尺寸闭合与 164B 差最终裁定

- 48 行长度求和：`28,892 = 0x70DC`（本卡脚本逐行累加并校验「上一行末端 == 下一行起点」，48/48 连续，无空洞无重叠）。
- 与 #36 oracle 一致（#36 的 28 对象 10,408 + 间隙 308 + st_Manager 17,504 + 头 88 + 字段区 552 + 尾 32 = 28,892）。
- **164B 差裁定**：`29,056 − 28,892 = 164 = 68 + 96`。
  - 68 = 注解尾部两员越过真实对象末尾：`mb_OK`（344B）@0x6FB8 的末端 0x7110（越界 52B）+ `mb_OKRc`（16B）@0x7110 整块在对象外；
  - 96 = `binary_size` 比最后成员末端 0x7120 又高出的尾填（洞清单 0x7120–0x7180 即此）；
  - 落地处置：`binary_size=28,892`，**删除这两员**；尾簇按本表 #38–#48 重建（Yes/Dicker/No 三个 344B + 152B 标题 + 标量 + flag + 3B pad），`mb_OK` 若保留名字必须落到 0x6EA4 那组 344B 控件（需成员级证据）。
- **st_Manager 块的处理**（占洞 16,968B/21 段）：建议 (a) 把 0x58 改为内联 union（`union { st_Manager m_PropData; struct { … } }`，块尺寸 0x4460），或 (b) 扩容 `st_Manager.binary_size=0x4460` 并把 21 个成员迁入 `st_Manager.json`；**禁止逐段补 byte 假闭合**（验收判据见 §6-7）。

## §6 实施卡步骤与验收检查点

步骤（建议顺序，每步可回退）：
1. 尺寸与尾段：`binary_size=28892`、删 `mb_OK/mb_OKRc`、按 §2 #38–#48 重建尾簇。
2. st_Manager 块：按 §5 方案 (a) 或 (b) 落地，洞 16,968B 归零。
3. 对象段：按 §2 逐行落 30 个对象（含 5×152、13×152、1208B、2×344 复合块）。
4. B- 段：先按「N 字节控件」占位 + 写补证 TODO，补证后再补类型（§3-③）。
5. 两处实例点 owner：`UISceneFrm+0xCC0`、`CUtil+0x6D4` 均标 `PropUI*`。
6. 基类：`bases` 是否改 UIListBox 另开证据轮，**不并入本实施卡**。

验收检查点（逐条对，来自 #36 §8 + 本卡）：
1. `binary_size == 28892`；生成树仍是 0x7180 判未落位。
2. vtable 恰为 0x56B688 七槽（slot5=`sub_46D4C0`，slot1/2/6=`0x43DDF0/0x46F620/0x46F650`）。
3. ctor 写界不越 0x70D8；出现 `+0x70DC` 及以上字段判错。
4. 十组建链锚点全中：`0x4DD0/0x5328/0x545C/0x6104/0x65CC(+0x20/+0x178)/0x68B8/0x6BD0/0x6D3C/0x6EA4/0x701C`，以及 `0x58` 的 0x4460 块。
5. 尾段不得把 `mb_OK` 平移到 0x6FB8（该偏移在 344B 控件体内）。
