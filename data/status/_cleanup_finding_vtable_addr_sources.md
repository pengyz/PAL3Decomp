# 发现：vtable 地址有**两个互不相交的数据源**，我此前混用（captain，2026-09-15）

## 事实（实测）

```
ctor 实写地址（IDA 导出 func_bounds.json 的 vptr_sites）: 467 个
注解记录的 vtable 地址（structs/*.json 的 vtables[].addr）:  93 个

★ 交集: **7 个**
★ 注解地址不在 ctor 实写集合里的: **86 个 (92%)**
★ ctor 地址不在注解里的: 460 个
```

**样例（注解有、ctor 无）**：`0x10000`（**明显不是合法表地址**）、`0x56A600`、`0x56AC08`、
`0x56AC20`、`0x56AE10`、`0x56B200`、`0x56D618`、`0x570A04`…

**样例（ctor 有、注解无）**：`0x574010`、`0x574C00`、`0x575010`、`0x579000`…

**交集（7 个）**：`0x56A9A4`、`0x56F5E4`、`0x56F7C8`、`0x56F8CC`、`0x56F9DC`、`0x56FA88`、`0x56FB34`
—— 恰好是 effect 族那几张（含我刚用作模板的 `CEffSParticle` 的 `0x56FB34`）。

## ⇒ 结论

1. **两批地址是不同来源**：注解是人写的（含 `0x10000` 这种脏值）；ctor 实写是字节事实。
2. **我此前把两者当作同一批使用（例如"注解 92 张表"、"ctor 边界法"），是错的。**
3. 这**解释了**为什么"F2 缺口 7 个类里 6 个得 0 分"：
   **我拿 ctor 地址集合去找它们的表，而它们（若曾被记录）用的是另一批来源。**
4. 也解释了 §8 的困境：**"哪个地址是某类的表"这个前提本身就不统一。**

## 对"下一步"的影响（任务定义改变）

原以为要做的是"**给缺口类补 `vtables`**"（写数据）。
**实际要先做的是"确定表地址的正确来源"**——否则写下的 `addr` 无法与已有 93 条一致。

**候选来源**：
| 来源 | 证据强度 | 问题 |
|---|---|---|
| ctor 实写的 vptr（`movl $0x56xxxx,(%reg)`）| **A 级**（字节事实）| 只覆盖"在该 TU 里构造的对象"；含 gbengine/`std::` 的库表 |
| `decomp` / IDA 的 vtable 引用 | 中 | 需统一口径 |
| 注解现有 93 条 | **低**（含 `0x10000`）| 是人写的，不一致 |

⇒ **在写任何 `vtables` 之前，必须先确定并记录"表地址的正确来源"**，
并**核对那 93 条注解地址是否可信**（`0x10000` 说明至少 1 条是脏的）。

## 诚实清单

- 本发现**否定**了我此前几轮的一个基本前提（"ctor 实写地址 = 注解用的表地址"）。
- 我**未**查明那 93 条注解地址的历史来源（可能有多个来源混杂）。
- 我**未**验证 `0x10000` 那条属于哪个类（可能是某次批量导入的脏值）。
