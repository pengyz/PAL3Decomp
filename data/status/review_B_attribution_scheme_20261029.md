**定谳**：
1. **错归属的产生端 = 认领战役批量产 claim**（上图产生端）。export_full.py:630 类名注入**不是产生端**——它把 vtable 认领**转写**成名形，是传播通道；IDA 类型传播同理是放大器（且制造信号回声）。三者中只有 claim 写入是"无中生有"的一环。

3. **用户担忧成立**：产生端无闸 ⇒ 下一场认领战役（R91 型）继续灌 unverified ⇒ 734 只是存量快照，队列无界增长。方案缺「新 claim 必须带证据级否则拒收」的闸——这是最小根因修复集的第 1 件（§4）。

## 3. 逐项攻防

### 3.1 B1 守卫（audit_attribution_guard.py）——信号设计与证据解剖错位

**实测重放**（与工具产出逐位对账：RED=505 复现一致 ✓）：

| 口径 | 数 | 证据 |
|---|---|---|
| 扫描认领 | 3934（总数 3935） | 重放 |
| 无 decomp 体（静默无信号） | 148 | 重放 |
| RED 505 中含**继承成员**（基类链闭包内） | **405（80.2%）** | 逐卡归因：成员级 946/1223（77%）为基类继承 |
| RED 中含「真缺席」成员（不在本类也不在基类链） | 116（纯真缺席 100） | 同上 |
| RED 中 decomp 名形类 ≠ 认领类（两套归属通道打架） | 94/505 | 例：claim=UIFrameWnd@0x442FF0，名形=CCBPanelSlot::Update_2ff0（该址即决策文档认定的 UIWnd 表 slot2 管理器巨型函数） |
| YELLOW 229 目标：type=skip 编译器生成 / ctor·dtor·thunk | 17 / 26 | 标注面实查 |
| Q 卡落在行表家族（63 类） | **408/734（56%）** | `_rowtable_family.json` 交集 |

| Q 卡证据级 | 714 unverified + 20 A（已带 A 级证据的争议件混排） | 重放 |

**必攻 1（根因）**：B1 的 `this->X` 证据通道有**信号回声**——IDB 类型来自被审 claim 本身（apply 写入），Hex-Rays 按认领类渲染成员名 ⇒ 真错归属的典型形态（cast 后调用、跨类调用 this）在体里**不以「异类成员」出现**，而以 `X::M((X*)this)` / `(X*)this` 参数形出现，恰是正则盲区。错位的 94 张卡更证明：RED 实际混装了「claim vs IDA 名形」两套归属通道的漂移，被误标为「成员反证」。
**必攻 2（合理性）**：RED 定级文案「错归属反证」**名不副实**——80% 是继承盲假阳（`∉本类索引` 被读成 `∉本类`，比已挂账的「∉索引≠∉类」更糟：索引连基类闭包都没有）。`CCBParabolaWindow::Render` 卡「missing m_rect」等三张抽样全是 UIFrameWnd/UIWnd 基类成员的合法继承访问。按用户规则这些不是「不准确的反证」，是**无信号**——应消卡而不是转人工。
**旗舰目标件缺席（记账失实实锤）**：`NPC::ResetLineupWindow`（0x00517CF0，NPC.json:173，unverified）是方案自设的目标案——体里 `CCBLineupWindow::Reset((CCBLineupWindow *)this, ...)`（参数形 cast，正则 `\(\((\w+) \*\)this\)` 不匹配逗号前的 `(X*)this`）⇒ 无卡。**250 张（B2b 时点）与 734 张（终态）两个版本里都没有它**，而 a50e2415c 提交信息宣称「NPC::ResetLineupWindow 目标件入卡 ✓」——被 a87229cb4 挂账的 known_blindspot 自述「目标件…缺席」直接证伪。自纠文化（第 4 例记账失实）只补落了盲区文案，B2b 的失实宣称未更正。
**测试假绿**：`test_attribution_guard.py` 全部用 list 形 `known_members: [{'name':...}]` 夹具；生产数据 933 个文件全部是 dict 形（`{"72": {name,...}}`）⇒ 测试绑定的是不存在的 schema（见 3.2）。

⇒ B2b 提交信息「ida_structs.data_members ∪ known_members（5 测）RED 反证 0→505（索引唤醒）」中，「双源」实为**单源**；「索引唤醒」的 505 全部来自 ida_structs 一侧。5 个测试全绿是因为夹具用了 list 形——**R11（改工具必须跑测试）执行了，但测试不绑定现实**（同型坑见 docs/knowledge/gotcha_dual_copy_table_divergence.md）。

### 3.3 B2a vtable 对账（audit_vtable_ownership.py）——P 档字节真值在实践里是空的

**字节读取器 bug（实锤）**：`dump_segment` 对 objdump -s 行内 4 个 8-hex 组逐 token 写 `mem[va+i]`，**va 不随 token 前进** ⇒ 每行只有最后一个 4 字节组落在行基址，其余被覆盖：

- 捕获 **47,572 / 196,608 字节（24.2%）**，可读 u32 位置仅 11,893（= 行数）；
- 手工核对 `CCBParabolaWindow` vtable：**7/7 槽在二进制 0x57058C 处逐槽吻合**（0x51CA50/0x51CAA0/0x51C9F0/0x51C880/0x445B90/0x51C260/0x51C9B0，objdump 直读）——工具却报 `TABLE_NOT_FOUND`。**正确的认领也验不了**。

**后果对账**：

| 产出 | 声称 | 实况 |
|---|---|---|
| 槽不一致 181 | 「非连续序列匹配细化队列」 | **181/181 全是 TABLE_NOT_FOUND**（184 个 vtable 认领中 181 个没找到表）——工具读不到字节的故障账，不是归属判定 |
| P:vtable_confirmed 2 | 字节真值确认 | 2 个都是**单槽认领**在幻影表址（行基址伪影：认领 0x5708cc → "定位" 0x5708c0=行基址）上的撞值；碰巧值对、址错 |
| P:misowned 3 | 错归属判定 | **3 条全是同一址 0x411B80**（Object/ScriptObj/GameObject 认领的共享析构/thunk；Role 等多表也持有）。其归属表全部 TABLE_NOT_FOUND ⇒ 「不在册」被判「misowned」。真相是**多类共享条目**（0x411B80 在 ≥5 个类的槽表里）——3 条 P 档判定全是假的 |

**设计层缺陷（独立于 bug）**：`classify_ownership` 把「认领类 ∉ owners-of-record」判为 `P:misowned`，而 owners-of-record 只收「已定位表 + 已过验槽」⇒ 表没找到 = 类不在册 = 假 misowned。**absence-based 判定违反「不准确=不判定」**——这正是 N1/C2065 灾难类的燃料（归属错不敢动的历史教训是「错判比不判更贵」）。
**覆盖率天花板（设计余项）**：vtable 槽只覆盖虚函数（184 表 / 行表家族 428 槽址），3935 认领含大量非虚件；且 MSVC6 调整 thunk/COMDAT 折叠（仓内有 `data/status/pending/adjustor_thunks.json`）⇒ 即使修好读取器，`槽值==入口址` 的精确相等也需 thunk 容忍（槽值 ∈ {入口, 删除析构 stub, 调整 thunk}）。
**结论**：P 档**准则**（字节真值第一）是对的；P 档**交付**当前不成立——先修 `dump_segment`（token 累进）与 `find_table`（逐槽锚定+窗口比对，弃全序列硬匹配），并把 misowned 改为**正向反证**（双方表都定位且认领类表实缺该槽）才可放行。

### 3.4 B2c Q 卡队列——经济学与「不准确=不判定」边界

**规则遵守**：RED 一律不自动判、只转人工 ✓；P 档只限字节真值 ✓（准则层合规）。
**但队列本身不可直接铺人裁**：

1. **约 80% RED 是继承盲机械假阳**（§3.1）——正确动作是消卡（补继承闭包），不是人裁；
2. **旗舰案缺席**（§3.1）⇒ 队列代表性失真：按它铺人裁会裁掉噪声、漏掉真鱼；
3. **卡无证据包**：卡面只有 class/addr/claim/missing 名单，没有 decomp 体摘录、xref、vtable/字节锚、基类链、认领出处——734 卡 × 每卡从零收集证据的成本远超卡数本身；20 张 A 级争议件与 714 张未验件混排，工作性质不同未分池；
4. **多认领强信号未结构化**：0x0043DE40 一址 18 类认领（Destroy__ovl_03 家族，review_dtor_identity_20261028.md 已立案）应是一张「多认领总卡」（认领清单+functions.json 无类+9×C2065+零定义产出的完整证据包，人裁分钟级），现状是按类拆成噪声卡；
5. **行表家族占 408/734**：这是传播端的系统性失真（行表注册制渲染污染），正解是行表语义处置（[ROWTABLE] 保真形 + 行表函数命名语义），处置后这批卡**整批改判或消解**——先裁它们等于给传播端 bug 付人件费；
6. **输出截断**：census 只存 red[:200]/yellow[:50]/slot_mismatch[:50]/misowned[:100]——判定产物丢证据，下游无法不重跑即消费。

### 3.5 盲区修补方案核（信号源切 pal3/src / 索引补缺 B2b-2）

- **信号源切生成 cpp（// 0xADDR 锚）**：必要——raw decomp 形确实漏掉 cast 参数形（旗舰案实证）。但它是**仪器修复**，不解决产生端；且切到生成 cpp 后信号经过 codegen stage 变换，需防新回声（stage 变换形 ≠ 语义形）。CAST 纳参数形 `(X*)this` 是低成本高回报件，应先做。
- **索引补缺 B2b-2**：若只在 guard 的 `build_member_index` 里补 dict 形 + 继承闭包，是**症状端绕**（私有索引修好了，annotation 层的成员缺口仍在，codegen/Hex-Rays 照旧缺成员）。正解：缺口成员在 **annotation 层**补（C 批成员化：CEffMgr 263 / SceneMgr 129 缺口成员，_b_workset_pin.md §4「批量定型的真实主场在 C 批，预实测可及率 75%/93%」），guard 索引只做只读合并。
- 两者都对，但**都打在症状/仪器端**——与「产生端闸」是不同层的活，不可互相替代。

### 3.6 优先级错位检查（L1 162 待爬 vs 734 人裁）

- 当前读数：`s4_baseline.json` L1 棘轮=162；S2 135/214（两份 S2 基线还互相矛盾 213 vs 214）；C1003 截断单元 1 个。CLAUDE.md 明文「字节匹配是第一优先级」。
- 归属治理对字节匹配的传导路径是**类布局正确 + 定义文件路由正确**，其高杠杆面恰是：① 多认领 216 址（路由错 = 定义进错类文件 → 字节差/C2065）；② 行表家族渲染形；③ 成员/类型缺口（B2 census 行表 231 条占位型行 + C 批 392 缺口成员）。
- **734 人裁既不在这条传导路径的高杠杆位（80% 噪声），又不阻断增量（无闸）** ⇒ 排序应为：**产生端止血（闸）→ 仪器修复（B2a/B1）→ 高杠杆件（行表 231 / 多认领 216 址）→ 再铺人裁（重构后的队列）**。用户的排序主张成立。
- 「行表 231」口径注：本复核能钉死的仓内同名计数是 `_b_workset_pin.md` §2「B2 行 type∈占位集 = **231**」（B2 census 占位型行，属 C 批成员化对象）；另一读法是行表（ROWTABLE）家族治理（408/734 卡 · 538 处标记 · 63 类）。两读法都是**产层/传播层高杠杆件**，优先级结论同向。唯一性见 §5。

## 4. 重定位建议 + 最小根因修复集

### 4.1 重定位一句话

**从「症状端普查 + 转人工」重定位为「产生端闸 + 证据仪器修复 + 高杠杆件先行，重构后的队列再人裁」**；P/Q/U 三档与「不准确=不判定」规则保留不动。

### 4.2 最小根因修复集（按序，前 3 件是止血）

| # | 件 | 层 | 内容 | 消什么 |
|---|---|---|---|---|

### 4.3 P/Q/U 边界修补（规则层一句话）

- P = **正向**字节真值（定位到表且槽值/形吻合）或等价 A 级指令证据；
- Q = 有反证但证据链不闭合（继承/索引/信号源任一不全）⇒ 只质疑不判定——**保留**；
- U = 无信号（不等于已验）——**保留**；
- **删除 absence-based 判定**：「不在册/表未定位/∉索引」永不产生 P 档判定（B2a 的 misowned 语义与 B1 的「反证」措辞都要按此改名：RED 的旗应叫 `Q:member_out_of_index`，不叫反证）。
