# 验证瓶颈论（立场 C · 对抗性复核）

> 2026-10-22 · 只出论证，未改任何产品文件。数据源：`data/status/_loop_last.json` ·
> `_d1_ledger.md:1634` · `docs/knowledge/gotcha_l1_reloc_dontcare_three_qualifications.md` ·
> `gotcha_verify_the_layer_before_patching.md` 等（逐条附出处）。

## 核心论点

1. **验证链成本 ≈ 生成链成本的 53 倍**。一次迭代实测：生成侧 apply 11.3s；
   验证侧 export 150.9s + codegen 199.5s + probe 59.9s + match 186s ≈ **596s**
   （`_loop_last.json` 三段 + `_d1_ledger.md:1634` probe/match 实跑）。
   改 annotation 1 分钟，等读数 10 分钟——迭代吞吐由验证决定，不由生成决定。
2. **验证不准 ⇒ 试错轮数被放大**。实测误判族至少 6 例（见下表）：pack(1) 假设被
   wine cl 证伪、`audit_layout` 恒等比较无判别力、PE 节范围误判"18 个 vtable 伪造"
   假发现、2026-10-19 陈旧验证把 S2 0/214 误读为改善、C1003 截断使门禁误判中性、
   L1 隐藏差异 19.24%。按 ~30% 误判率折算：每 10 轮有 3 轮读数不可信，
   需额外一轮复核 + 一轮回滚 ⇒ **等效成本 ×1.5~1.8**。
3. **误判的代价不止时间，更是注意力**。元/实 ~7:3 的直接成因是大量会话轮次消耗在
   「先证明读数是真的」而非「推进实质」；`gotcha_verify_the_layer_before_patching.md`
   记录连续 **12 次**先猜后动手零效果/净回归——根因是验证反馈太慢太糙，
   每次只能靠猜填补等待。
4. **降验证成本是最高 ROI**。生成/annotation 侧已有多道纪律（证据分级、四道门、
   病灶层三问），边际收益递减；而验证侧全串行、零增量、零缓存，存在**数量级**的
   砍削空间。验证快且准 ⇒ 单位时间有效轮数↑ ⇒ 元/实比例自然回落。
5. **验证准是验证快的前提**。缓存/并行若作用在错误读数上只会更快地错——
   先修判据（stale 检查、C1003/L1 三限定显式化），再谈加速。

## 承认反驳

- **生成/annotation 确实重要**：L1 最终由源码字节决定，标注错误必须在 annotation 层修
  （病灶层三问是正确纪律）。验证快不会自动产生正确标注。
- **快 ≠ 允许试错**：CLAUDE.md「禁止试错式修改」红线不因验证提速而松动——提速的用途是
  **快速证伪假设**，不是批量盲改。
- **部分验证耗时是本质成本**：MSVC6 wine 编译、全量字节比对不可零化；本论主张砍的是
  冗余（串行/全量/重复），不是判据本身。
- **度量盲区是判据缺陷不是速度问题**：C1003 截断、L1 三限定需在引用层修，与并行化正交。

## 具体方案（按 ROI 排序）

1. **增量验证（最高 ROI）**：按 annotation diff 的影响闭包只重导出/重编译受影响单元，
   probe/match 只跑 delta。单类改动从 607s → 预计 **<60s（×10）**；全量仅在提交前跑。
   实现锚点：`annotation_diff.py` 已有变更摘要，可做影响面传播。
2. **codegen/probe 并行化**：210 个单元彼此独立，Ninja 已并行编译但 stage 管道串行；
   probe 按单元分片到多进程 ⇒ 199.5s+59.9s → 预计 **~60s（×4）**。
3. **缓存**：export 结果按 IDB mtime+annotation hash 做键缓存（未变则跳过 150.9s）；
   codegen 中间 stage 同理。未变更迭代 → **apply-only 11.3s**（×53）。
4. **误判率治理（准优先）**：① `loop` 强制 stale 检查（`ida_structs.json` 时间戳门，
   治 2026-10-19 误读）；② C1003 截断单元表 + L1 三限定随数字自动打印；
   ③ match 恒红项显式化为「假失败清单」，防止当退化。目标误判率 ~30% → **<10%**。

**预期收益**：验证链 596s → 常规 <60s、全量 ~200s；可信轮数 6/100min → **40+/100min**；
误判返工减少 ⇒ 元/实 7:3 → **5:5 以上**。S2/L1 的推进速度由「每小时可信读数次数」决定，
这正是验证瓶颈的杠杆点。
